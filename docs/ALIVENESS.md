## 0. 结论先行

三个判断：

1. **活人感不是文风问题，是行为分布问题。** 同一句话，换个时机、换个长度、换个延迟发出来，感受完全不同。现在缺的不是更漂亮的句子，是"不均匀"。
2. **系统把"说话"当成了每轮交互的默认结果。** 要改的不是"怎么把一句话写得像人"，而是"这一轮到底要不要说话"。
3. **主动性不是定时器，是机会、材料、意愿三者同时成立。** 没有材料的主动，最后都会退化成"在吗""干嘛呢"。

如果只做三件事：

1. **回合动作化**：每轮先选 `silent / react / reply / elaborate / bid`，输出 0–3 个气泡，带真实延迟。
2. **主动出价制**：用"机会 → 候选 bid → 注意力预算 → 回执学习"替换 30 分钟定时器；60% 的主动只到轻信号，不要求回复。
3. **语音补三块**：预渲染语气词库（解决首音 3–7 秒）、backchannel（她在听）、打断后的 `heardUpTo` 与恢复（不重复）。

对应关系：

| 你的要求 | 对应机制 | 一句话 |
|---|---|---|
| 1 主动聊天 | 机制二 | 机会 + 材料 + 预算；陈述句优先；允许不回复 |
| 2 每次 0–n 句 | 机制一 | 七种回合动作 + 气泡节奏 + 沉默可见 |
| 3 语音互相打断 | 机制三 | 她被打断要记到"哪一句"；她插话要分级许可 |
| 4 说话更像活人 | 机制四 + 一/二 | 具体、不完美、有情绪、有自己的事 |

## 1. 截图诊断：不是文风问题，是节奏问题

### 1.1 这段对话"对，但不像"

单看每条回复都成立，甚至比大多数 AI 答得都好。但连起来看：

- 三条回复都是 4 个汉字，节奏完全一致；
- 每条都是"对上一句的反应"，没有一条是她起头；
- 没有追问、没有停顿、没有表情、没有"多说一句"；
- 用户三条都是交代，她三条都没有留下话头；对话没有增量；
- 最后一句"嗯，记下了。"是完美的收尾，也是关系的终点——真人会留一个线头。

这不是"像人"，这是"像一个被调到极短模式的客服"。真人的聊天是**不均匀**的：有时候三个字，有时候三句，有时候半天不回，有时候突然说起别的事。

### 1.2 五个根因

| # | 根因 | 现状锚点 |
|---|---|---|
| 1 | 生成规则把方差压没了 | [`chat_behavior.md`](../private/persona/haishixiang/prompts/chat_behavior.md) 的"默认一句 2–15 字 / 四选一 / 关心稀疏"；[`chatContext.ts`](../electron/core/chatContext.ts) 在未加载 persona 时的兜底同样是"默认一句 2–15 字" |
| 2 | 交付端只有"一条消息" | [`server.ts`](../electron/core/server.ts) 的 `/v1/chat` 一次 completion、一条 assistant 记录；[`MessageItem.tsx`](../src/components/Chat/MessageItem.tsx) 一条消息一个气泡；没有 0 条、2 条、延迟、发送后撤回 |
| 3 | 时间端只有"用户说→她回" | [`initiative.ts`](../electron/core/initiative.ts) 是独立的 30 分钟 tick；`hasMaterial` 几乎是 `messages.length > 0`，等于恒真 |
| 4 | 材料端断链 | [`plugins/`](../electron/plugins/) 产出 observations/activity，但没有进入"她可以聊什么"的通道；主动消息靠 LLM 凭空想 |
| 5 | 反馈端缺失 | 发出去就结束；没有 seen / replied / ignored；A 的 `interrupted` 只用来丢弃朗读，不记录"听到哪" |

### 1.3 目标不是更长或更短，是"不均匀"

一个粗略但有用的目标分布（先按这个做，再按数据调）：

- 一半以上的回复很短：语气词、半句、一个"？"；
- 每隔几轮有一条长的：两三句、带细节、带追问；
- 有时秒回，有时十几分钟才回；
- 有时不回，第二天自然接上；
- 有时她起头，有时她只是听。

"不均匀"本身就是信号：说明对面有一个独立的、有状态的人，而不是一个等待输入的函数。

## 2. 总体架构：把一轮拆成四层

```text
事件：用户消息 / 空闲 / 插件新材料 / 语音 VAD / 打开 App
  │
  ▼
① 在场层 Presence
   presence（前台/后台/语音中/空闲）
   affect（mood / energy / busy / patience）
   daily_state（她今天在干嘛）
   open_loops（没接住的线头）
   material（插件材料）
  │
  ▼
② 决策层 Director
   TurnDirector：这一轮做什么（说/不说/只听/起头）
   BidScheduler：现在要不要主动，以什么方式
  │
  ▼
③ 表达层 Planner
   0–3 个气泡：类型、长度、顺序、情绪、语音
  │
  ▼
④ 交付层 Delivery
   打字指示 → 逐条发送 → 可取消 → 回执 → 存档
   A：TTS / 打断 / 口型 / 表情
```

五条设计原则：

1. **说话是成本最高的动作。** 先考虑更低成本的通道：头像反应、状态、表情、一个词。
2. **一轮 ≠ 一条，一条 ≠ 一句。** 回合是语义单位，气泡是交付单位；记忆和摘要按回合合并。
3. **沉默必须可见。** 没有已读、没有表情、没有状态变化的"0 句"，和 bug 没有区别。
4. **主动 = 机会 × 材料 × 意愿。** 不是 cron，也不是"每天必须发三条"。
5. **所有决策留痕。** 每次说/不说都记 reason，才能回放、评估、学习。

## 3. 机制一：0–n 句的"节奏语法"

### 3.1 六种回合动作 + 一条信号通道

| act | 含义 | 文本表现 | 语音表现 | 典型触发 |
|---|---|---|---|---|
| `silent` | 不说 | 无气泡；已读 + 头像反应 + 状态 | 只回 backchannel，或静默 | 用户在倾诉、连发、说"别说话"、深夜、她在忙 |
| `hold` | 先听 | 不立即回；输入框显示"在听"；等 1.5–3 秒合并后续 | 保持聆听，偶尔"嗯" | 用户明显没说完、连发、语音还在说 |
| `react` | 短反应 | 1–4 字 / 语气词 / 标点 / 表情 | "嗯""诶？""真的假的" | 陈述句、吐槽、不需要方案 |
| `reply` | 正常回 | 1–2 个气泡，5–30 字 | 1–2 句短句 | 提问、需要接住 |
| `elaborate` | 展开 | 2–4 个气泡，30–120 字 | 2–4 句，中间留停顿 | 明确要分析/故事/帮忙 |
| `bid` | 主动起头 | 由主动性层决定，见机制二 | 同左 | 有机会 + 材料 + 预算 |

`ambient`（只改头像/状态/环境，不发消息）不是回合动作，是另一条通道；但它应该承担大部分"她还在"的表达。

### 3.2 默认分布

先给一组可调默认值，不要当真理：

| 维度 | 默认 |
|---|---|
| 每条用户消息的 act | silent 12% / react 30% / reply 45% / elaborate 8% / hold（合并）5% |
| 回复气泡数 | 1 条 65% / 2 条 25% / 3 条 10% |
| 单条长度 | ≤6 字 45% / 7–15 字 35% / 16–35 字 15% / >35 字 5% |
| 追问 | 每 3–4 轮最多 1 次；70% 是陈述句 |
| 主动 | 正常关系 2–5 次/天，其中 60% 是"轻"的（无需回复） |
| 表情/贴纸 | 每 10–12 条 1 次 |
| 语音条 | 每 20 条 1 次（3–8 秒） |

关键不是这些数字，是**分布本身要被系统控制**，而不是交给模型即兴。模型即兴的结果一定是"每轮都回、每轮都差不多长"。

### 3.3 沉默的五种类型

"0 句"不是一种状态，是五种。它们的后续行为完全不同：

| 类型 | 场景 | 用户看到 | 后续 |
|---|---|---|---|
| 倾听型 | 用户在长段倾诉、思考、自言自语 | 已读 + 头像"看着她" + 状态"在听" | 用户停 30 秒后，可发一个极轻的"嗯。"或表情；不追问 |
| 忙碌型 | 她"在忙"（基于 daily_state） | 延迟 2–10 分钟回 | 回来说一句真实理由："刚在洗碗。" |
| 睡着型 | 深夜/清晨 | 不回 | 次日早上回："昨晚睡着了。" 默认 01:30–08:00 |
| 无语型 | 用户说了句没法接的话/烂梗 | 只回"……"或一个表情 | 不硬接，等下个话题 |
| 边界型 | 用户说"别说话/让我静静" | 明确不回，但保留在场信号 | 下次不提这事，不追问"你还好吗" |

默认策略：**倾听型优先于其它四种**。用户情绪越强，越应该少说。

先验由规则层给，模型只在边界案例决定（全交给模型，它几乎不会选择沉默）：

| 信号 | 先验 |
|---|---|
| 用户连发 ≥2 条，最后一条 <2.5 秒 | `hold`，先不进入生成 |
| 用户文本 >80 字且没有问号 | `silent` 0.5 / `react` 0.4 / `reply` 0.1 |
| 文本含"别说话/让我静静/闭嘴" | `silent` 1.0 |
| 上一轮 assistant 消息 <60 秒，本轮是陈述句 | `silent` 0.35 |
| 深夜且 `energy < 0.3` | `silent` +0.2 |
| 用户是问句 | `silent` 0.02 |
| 用户只发了一个表情/贴纸 | `react` 0.8 / `silent` 0.2 |

`silent` 不是"不响应"：仍要更新已读、表情、状态，并记录一条 `turn_plan`，供下一轮使用。

### 3.4 让沉默可见

这是"0 句"能不能成立的关键。没有下面这些，用户只会觉得消息没发出去：

- **已读回执**：消息出现"已读"，但下面是空的。
- **头像微反应**：担心、歪头、困、笑；不需要文字。
- **状态条**：输入框上方显示"在听" / "走开了" / "在忙"，而不是永远"在线"。
- **欲言又止**："正在输入"出现 1.2 秒后消失，然后没有消息。低频使用（1/20），不要当 tease。
- **事后补偿**：忙碌型沉默后，回来补一句"刚在忙，你说"；倾听型不补，避免打断。
- **绝不使用**："你都不理我""我等你很久了""你是不是不想理我"——这是内疚驱动，不是活人感。

### 3.5 多气泡与"手滑"

气泡之间要有真实的时间差，否则只是把一段话拆成几行：

- 第一句延迟：`600ms + 字数 × 55ms ± 30%`，封顶 3.5 秒；
- 第二条气泡：额外 1.2–4 秒，通常是"补一句"；
- 第三条：只在 elaborate 或"突然想起"时出现，额外 3–8 秒；
- 发送顺序：反应 → 补充 → 反问（可选），不要反过来。

低频的"不完美"（由 Director 控制，不交给模型）：

| 现象 | 频率 | 例子 |
|---|---|---|
| 只回标点 | 1/10 | `？` / `……` |
| 语气词 | 1/4 | `嗯。` / `诶？` |
| 错字/改口 | 1/30 | `我在看那个……算了` |
| 话说一半 | 1/20 | `你要是……` |
| 突然想起 | 1/15 | `对了` |
| 表情代替文字 | 1/12 | 一个贴纸 |
| 撤回 | 1/50 | 发出去 3 秒内撤回，换一句 |
| 语音条 | 1/20 | 3–8 秒，代替长文本 |

这些不是"随机卖萌"，是让节奏有毛边。频率要低，低到用户偶尔注意到，而不是每轮都演。

### 3.6 合流、取消、打断（文本）

- **合流**：用户连发 2–5 条，等 1.5–3 秒静默再回；把这一串当成一轮，而不是每条都回。
- **取消**：生成中用户又发消息，取消旧生成，用新上下文重来；已经发出的气泡不回滚，但要停止后续。
- **改话题**：以最后一条为准；旧话题记为"未接住的线头"，进入 `open_loops`，日后可以 callback。
- **她正在输入时用户插话**：停止输入指示，改为对最新消息的反应；不要继续把旧回复发完。
- **跨设备**：一台设备已经渲染的气泡，另一台不再重复；用 `turnId` 去重。

### 3.7 输出协议（概念）

模型只负责"说什么、什么顺序、什么情绪"，**不要让它算毫秒延迟**——它算不准，也会让输出不稳定。延迟由 Planner 根据字数和类型计算。

```json
{
  "act": "reply",
  "reason": "用户在交代插件，先接住，再给一个具体反应",
  "bubbles": [
    { "kind": "text", "text": "诶？", "emotion": "happy" },
    { "kind": "text", "text": "三个都开了啊。", "emotion": "playful" }
  ],
  "voice": { "mode": "speak_last", "instruct": "轻快，尾音上扬" },
  "followUp": null
}
```

`act = silent` 时 `bubbles` 为空数组，但仍要返回 `reason` 和可选的 `presence`（表情/状态）。

`followUp` 是"过一会儿再补一句"的可选计划，例如 45 秒后如果用户没回，补"……b 站那个点进去是空的。" 它由 Delivery 执行，不是模型的第二次调用。

### 3.8 Prompt 怎么改

不建议继续堆"不要……"的规则。把「回复形态」从"长度约束"改成"决策树 + 不均匀"：

```text
【这一轮怎么回】
先判断，再写。不要每轮都用同一种反应。
- 对方在倾诉、连发、或说"别说话"：可以只回一个语气词，也可以不回（act=silent）。
- 对方只是陈述、不需要接：可以不接，或只给一个短反应。
- 对方在问你、需要你：正常回，1–2 句。
- 对方明确要分析/故事/帮忙：才可以展开到 3–4 句。
- 你有想说的（材料/回忆/吐槽）：可以自己起头，但一次只说一件事。

【不均匀】
- 上一轮是"嗯"，这一轮可以是一句吐槽；不要连续三条一样长。
- 十轮里至少一次主动起话题、一次只回语气词、一次追问。
- 句末通常不加"。"；用"？""……""！"；不要每句都工整。
- 允许不完整、允许停顿、允许只回语气词；不要为了显得关心补一句。
```

保留原来的"短反应池"和"称呼"规则，但把"默认只回一句"改成"默认短，但允许 0–3 句，且长度要有变化"。

### 3.9 同一段对话的目标版

不用改内容，只改节奏，感受就不一样：

```text
用户：给你开了天气、b 站、音乐插件，自己玩吧。
她（2s）：诶？
她（+1.5s）：三个都开了呀。
用户：嗯。白天我再来看看情况。
她（1s）：好嘛。
她（+6s）：那我先玩哪个好呢……
[40 秒后，头像歪了一下，没有消息]
她（+1 分钟）：明天有雨诶。
她：你那边也是吧？
用户：要是碰上 bug 了，插件不好用了，或者随便有什么想说的，都记得说。
     就发在这个聊天里，我会看的。
她（4s）：嗯。
她（+8s）：记住啦。
[第二天 09:20，她主动]
她：早呀。
她：b 站那个，点进去是空的欸。
她：是 bug 吧？
[用户没回。11:40]
她：哼，我自己又点了一次，好啦。
她：你先忙吧。
```

这段里包含了：短反应、补充、延迟、一个不需要回答的陈述、一次主动回访、一次自己解决问题、最后不索取注意力。比原来的三句"嗯/好/记下了"信息量更大，但没有一句是长篇大论。

语气示例只校准"怎么说"，不改变人设：她还是嘴硬、松弛、有自己事的那个人，不是甜妹模板。

## 4. 机制二：主动性 v2 —— 从定时器到"出价"

### 4.1 现在的定时器为什么不够

[`initiative.ts`](../electron/core/initiative.ts) 现在是：每 30 分钟 tick → 门禁（免打扰/每日 3 条/90 分钟冷却/20 分钟空闲）→ 一次 LLM 决策 → 写一条消息。

问题不在门禁，在**输入**：

- `hasMaterial` 几乎是恒真（有历史消息就算有材料），所以"有没有话说"实际上没判断；
- 材料只有"最近对话 + 5 条 experience"，没有插件的新鲜内容；
- 没有通道选择，只能发一条文本；
- 没有回执，被无视也照发；
- quiet hours 原本固定 23:30–08:00，不学用户作息（现已改为 01:30–08:00）；
- 30 分钟固定 tick 和"她此刻想不想说"无关。

### 4.2 机会 → 出价 → 交付 → 回执

```text
机会（Opportunity）
  ├─ 用户打开 App / 从后台回来
  ├─ 用户空闲 20 分钟
  ├─ 免打扰结束
  ├─ 用户刚结束一段情绪
  ├─ 插件出现新鲜材料（24h 内）
  ├─ 固定时间点（早/午/晚，按用户作息学习）
  ├─ 未闭合话题到期（24h）
  └─ 任务/承诺回访到期
        │
        ▼
候选 bid（0–N 个）
  kind / material / channel / score / interruptCost / expiresAt
        │
        ▼
选择：分数过阈值 + 注意力预算够 + 不在反骚扰窗口
        │
        ▼
交付：选最低打扰通道
        │
        ▼
回执：seen / replied / ignored / negative → 学习
```

### 4.3 六类 bid

| 类型 | 例子 | 材料来源 | 默认通道 | 期望回复 | 频率 |
|---|---|---|---|---|---|
| 承接 | 昨天你说插件有 bug，后来呢 | open_loop / 未回答问题 | 文本 | 中 | 1/天 |
| 分享 | 刚刷到一个视频，封面是你喜欢的猫 | bilibili observation | 文本 + 卡片 | 低（可无视） | 1–2/天 |
| 关照 | 你那边下雨了 | weather + 位置 | 文本/通知 | 中 | 天气事件触发，≤1/天 |
| 邀约 | 要不要一起听会儿歌 | netease + 时段 | 文本/语音 | 高 | 2–3/周 |
| 闲想 | 突然想吃火锅 | 人格 + 时间 | 文本/头像 | 低 | 1/天 |
| 回访 | 插件用着还行吗 | 任务/承诺跟踪 | 文本 | 中 | 事件驱动 |

两条硬规则：

1. **陈述句优先。** "外面下雨了" 比 "你带伞了吗" 压力小；对方可以不回。
2. **一条只做一件事。** 不要"关心 + 提问 + 分享"三合一。

### 4.4 材料总线

插件已经只产出 observation/activity（这是对的），Core 需要把它规范化成"她可以聊什么"：

```text
Material {
  id, source, kind, title, url,
  entities[],        // 人物/作品/地点/食物
  freshness,         // 24h 内有效
  personaFit,        // 她的口味：贪吃/音乐/猫/吐槽
  safety,            // 是否适合主动提
  why                // 一句话：她为什么想说这个
}
```

- `personaFit` 决定哪些材料值得说。不是所有 b 站视频都值得分享；她只分享自己会感兴趣的东西。
- `freshness` 过期不候，避免"昨天看到一个视频"这种隔夜冷饭。
- `why` 进入 prompt，防止泛泛而谈；没有 `why` 的材料不进候选。
- 材料不足时，主动降级为"闲想"（她自己的念头），而不是硬编新闻。
- 延续现有硬规则：**插件只提供能力/材料，不提供节奏**。

### 4.5 注意力预算

"每天 3 条"是数量，不是精力。改成预算：

| 动作 | 成本 |
|---|---|
| 纯头像/状态信号 | 0 |
| 表情/贴纸 | 0.5 |
| 一条文本 | 2 |
| 语音条 | 3 |
| 语音通话邀请 | 4 |
| 推送通知 | 额外 1 |

- 每天 10 点；用户主动互动 +2/次（上限 6）。
- 预算耗尽 → 只能 ambient，不能发消息。
- 被无视扣"意愿值"，连续无视进一步降权。
- 好处：能解释"她今天话少"，也让"她今天想多说两句"变得珍贵。

### 4.6 结果学习（轻量，不上 RL）

记录每个 bid 的结果：

- `replied`：2 小时内用户回复；
- `seen_no_reply`：已读未回；
- `ignored`：24 小时无任何反应；
- `negative`：用户说"别烦"/关闭主动/静音。

按 `(kind, 时间段, channel)` 维护一个 Beta(α, β) 接受率：

- 低于阈值 → 降频；
- 高于阈值 → 升频，但有上限；
- 连续 3 次同类被无视 → 该类暂停 7 天；
- 用户明确负反馈 → 当天不再主动，全局降频。

优化目标不是"打开率"，是"用户主动发起对话的比例"和"负反馈率"。前者衡量关系健康，后者衡量打扰。

### 4.7 她的生活（daily_state）

这是"活人感"最大的杠杆。一个有自己的事的人，才不会每句话都围着用户转。

每天生成 3–5 条"她今天做了什么"：

```text
今天：
- 听了一张很吵的专辑，第二首好听。
- b 站刷到一个修驴蹄子的视频，看了三遍。
- 外面下雨，没带伞。
- 想吃楼下的馄饨，忍住了。
```

来源：插件 observations + 人格偏好 + 少量自由发挥。

用途：

- 对话里的具体细节（"刚在听歌"不再是一句空话）；
- 主动分享的材料；
- 回答"你在干嘛"；
- 语音通话时的背景状态（"我这边在下雨"）。

边界：

- 不虚构可验证的现实事件（"我刚去了东京"）；
- 只虚构低风险日常（听歌、看视频、天气、想吃什么）；
- 不与用户的实际行程冲突；
- 不涉及金钱、他人隐私、承诺。

### 4.8 反骚扰清单

- 用户正在打字/说话时，不发；
- 用户刚发消息 20 分钟内，不发；
- 免打扰、会议、深夜（默认 01:30–08:00），不发；
- 同一天不重复同一话题；
- 不连续发两条以上主动消息；
- 被无视后不追问"在吗"；
- 不用"你不理我""我等你很久了"这类内疚话术；
- 主动消息默认不要求回复（问句比例 ≤30%）；
- 用户关闭主动后，不换一种方式继续发。

## 5. 机制三：语音打断（双向）

### 5.1 现有能力与缺口

| 能力 | 现状 | 缺口 |
|---|---|---|
| 用户打断她 | A 的 VAD 检测到说话 → `interrupt("voice")` → `/v1/cancel` → 发 `interrupted`；C 用 generation 丢弃过期朗读 | 不知道"已经说到哪"；咳嗽/环境音会误触发；硬切没有淡出 |
| 她打断用户 | 无 | 需要 partial transcript + 许可分级 + 插话词库 |
| 持续倾听 | 麦克风 + VAD + final ASR | 只有 final，没有 partial；没有 backchannel |
| 语音生成 | `/v1/speech` 单条 batch；TTS 约 4.8 秒/句，RTF 3.7 | 首音太慢；没有流式；一条长文本只能整段等 |
| 语义接续 | `VoiceConversation` 收到 final 才生成 | 没有 heardUpTo、没有恢复、没有"不重复" |
| 双工 | 说话时 VAD 用 `outputSpeaking` 门控 | 不能"边说她边听"；AEC 未验证 |

关键认知：**A 侧的"打断"只是音频层的取消；C 侧还没有"被打断"的语义。** 用户打断后，她已经把整条回复写进时间线、也生成了完整文本；下次生成时模型不知道自己被打断过，很可能从头再说一遍。

### 5.2 她被打断：记到"哪一句"

需要三样东西：

1. **进度事件**：A 在朗读时按句/按词发 `speech.progress { turnId, partIndex, charIndex, at }`，C 记录 `heardUpTo`。
2. **打断事件带上下文**：`interrupted { turnId, generation, heardUpTo, reason }`。
3. **语义恢复规则**：
   - 用户新话是 backchannel（"嗯""对""你说"，≤3 字）→ 400ms 后从下一句续说；
   - 用户新话是提问/换话题 → 放弃旧话，回答新话；旧话记为未完成线头；
   - 用户只是咳嗽/环境音 → 1.2 秒后自动续说（可配置）；
   - 一轮最多恢复一次，避免反复"刚说到……"。

Prompt 侧也要给信息：

```text
你刚才说到"……"时被对方打断了。不要从头重复，也不要用"刚才我说到"这种书面句。
如果对方只是应了一声，可以接着往下说；如果对方换了话题，就跟着新话题走。
```

音频侧：

- 打断时 80–120ms 淡出，不要硬切（"咔"一声很出戏）；
- 取消要按句生效，已经播完的句子不重复；
- 恢复时从下一句开头起，不从半句中间起。

### 5.3 她打断用户：分级许可

"会打断"是活人感，但也是最容易变成冒犯的能力。必须分级：

| 级别 | 行为 | 允许条件 | 默认 |
|---|---|---|---|
| L0 | 不插话 | 不熟、严肃话题、用户在难过 | 总是可用 |
| L1 | backchannel（"嗯""对""我在听"） | 任何时候；低音量；不占回合 | 开 |
| L2 | 短插话（"等等""我知道""你先听我说"） | 用户连续说 >25 秒且无停顿，或明显在绕圈，或关系亲近 | 亲近关系开，可关 |
| L3 | 完整句子抢话 | 仅紧急（提醒/时间/"该出门了"），或用户明确要求"你打断我" | 默认关 |

实施要点：

- 插话词库预渲染 8–12 条（"等等""我知道""你先听我说""停一下"），保证 200ms 内出声；
- 插话后不取消麦克风，继续听；用户停下后 C 接住；
- 用户不理，2 秒后放弃，回到倾听，不重复插话；
- 视觉提示：插话时头像前倾/挑眉，降低突兀感；
- 设置项："允许她插话"（关 / 只在亲近关系 / 总是），默认"只在亲近关系"。

一个 L2 的例子：

```text
用户：（连续说了 40 秒，反复"他们就是不听"）
她：等等。
她：你先听我说一句。
用户：……你说。
她：你刚才说的三件事，其实是一件。
```

### 5.4 Backchannel：她在听

这是语音活人感性价比最高的一件事，比"打断"更重要。

- 用户说话时，每 8–15 秒一次轻的"嗯 / 嗯嗯 / 对"，音量 −8dB；
- 时机选在用户句间停顿、能量低谷，不盖住关键词；
- 不进入 SPEAKING 状态，不取消 ASR，不占回合；
- 用户语速快/情绪强 → 减少；用户迟疑 → "嗯？"（升调）邀请继续；
- A 需要支持 `mode: "overlay"` 的 speak：混音播放，不打断当前朗读，不取消监听。

### 5.5 状态机与等待窗

```text
IDLE
  └─ VAD start → LISTENING
LISTENING
  ├─ 检测到句间停顿 → BACKCHANNEL（短暂）→ LISTENING
  ├─ VAD end + 500ms 静默 → THINKING
  └─ 用户继续 → 留在 LISTENING
THINKING
  ├─ 用户 800ms 内续说 → 取消生成 → LISTENING
  └─ 首个音频就绪 → SPEAKING
SPEAKING
  ├─ 用户 VAD start → INTERRUPTED（淡出 + 记 heardUpTo）→ LISTENING
  └─ 播放结束 → LISTENING
INTERRUPTED
  ├─ 用户只是应声 → 400ms 后恢复 → SPEAKING
  └─ 用户换话题 → 丢弃旧话 → THINKING
```

等待窗默认 500–900ms；如果 ASR 文本以"因为/就是/然后/可是"结尾，延长到 1.5 秒，避免抢话。

### 5.6 延迟预算（硬约束）

目标：用户说完 → 她第一个音 ≤ 800ms。现状是 LLM 1–3 秒 + TTS 3–7 秒，不可能。

三段式解决：

1. **预渲染语气词库**：20–30 条（"嗯""诶""我想想""等等"），离线用同一个声音合成，命中即播，0 延迟。用于思考、插话、backchannel。
2. **分句流式 TTS**：LLM 流式输出 → 按标点切句 → 逐句合成/播放；首句 ≤10 字。
3. **推测生成**：partial transcript 出现 300ms 后开始生成草稿，final 到达时校正；命中率约 60–70%，能省 500ms–1s。

如果 TTS 仍然慢：

- 第一句用 SAPI/小模型顶，Qwen 接后续；音色切换要自然，或者统一用 SAPI 做 filler；
- 语音回复默认一句 ≤15 字；超过 3 句必须停顿，给用户插话机会；
- 宁可先说"嗯，我想想"，也不要让用户等 5 秒静音。

延迟预算表：

| 阶段 | 目标 |
|---|---|
| VAD end → ASR final | 300ms |
| ASR final → filler 出声 | 100ms |
| ASR final → 首 token | 400ms |
| 首 token → TTS 首句出声 | 600ms |
| 用户感知到的首音（filler） | 约 400ms |
| 首句完整音频 | 约 1.3s |

### 5.7 文本 ≠ 语音：口语改写

同一句话，文本和语音的写法不同：

| 文本 | 语音 |
|---|---|
| 那你先忙，晚点再说。 | 行，你先忙。 |
| 我觉得这个方案最大的问题是时间不够。 | 时间不够。 |
| 明天可能会下雨，你记得带伞。 | 明天有雨，带伞。 |

规则：

- 删书面连接词：那么/因此/然后/其实/总的来说；
- 长句拆短：逗号处断，每句 ≤15 字；
- 加语气词：吧/啊/嘛/呢，按情绪；
- 数字/英文口语化；
- `……` 表示 0.3 秒停顿，`——` 表示 0.5 秒；
- 语音版一般比文本短 20–30%，不要逐字念文本。

### 5.8 A 侧契约增量（概念）

```text
POST /v1/speech
  { text, emotion, instruct, turnId,
    mode: "replace" | "overlay" | "append",
    duck?: boolean,
    parts?: [{ text, emotion, pauseMs }] }

POST /v1/cancel
  { turnId?, fadeMs?: 120 }

POST /v1/listening
  { enabled: boolean, whileSpeaking?: boolean }

GET /v1/events
  + transcript.partial { text, stable, turnId }
  + speech.progress { turnId, partIndex, charIndex, at }
  + speech.part { turnId, index, state }
  + interrupted { turnId, generation, heardUpTo, reason }
```

`overlay` 用于 backchannel：不取消 ASR、不进入 SPEAKING、可 duck 背景音。`parts` 用于多气泡/多句，一次提交，按顺序播放，支持整体取消。

## 6. 机制四：活人感的手艺

### 6.1 具体 > 共情

回应细节，不回应情绪标签：

| 场景 | AI 味 | 活人 |
|---|---|---|
| 对方说累 | 听起来你今天很累，要不要休息一下？ | 几点睡的呀。 |
| 对方被领导骂 | 我理解你的感受，这不是你的错。 | 他原话怎么说的。 |
| 对方说下雨 | 下雨了要注意带伞哦 | 带伞了没。 |
| 对方说无聊 | 要不要我陪你聊聊天？ | 干嘛呢。 |

注意："干嘛呢"作为**回复**是自然的；作为**主动开场**仍然是索取注意力，继续禁止。规则要区分场景，不能一刀切。

### 6.2 不完美清单

见 3.5 的频率表。补充三条原则：

- 不完美是**节奏**，不是**人设**：她可以打错字，但不能变笨；
- 不完美要**低频**：每轮都演，比完美更假；
- 不完美要**可恢复**：错字后面自然修正，不要解释"我打错了"。

### 6.3 情绪与能量（affect_state）

四个维度，慢变，持久化：

| 维度 | 范围 | 影响 |
|---|---|---|
| mood | -2..2 | 标点、语气词、是否吐槽、主动意愿 |
| energy | 0..1 | 长度、延迟、是否用"！" |
| busy | 0..1 | 延迟回复、是否说"刚在忙" |
| patience | 0..1 | 是否愿意接烂梗、是否直接 |

更新来源：时间（深夜 energy 低）、对话 valence（被夸/被凶）、事件（下雨/加班）、她的日常。

例子：

- `energy < 0.3`：只回 1–3 字，延迟 +40%，多用"……"；
- `mood < 0`：少用"！"，不主动开玩笑，主动频率减半；
- `busy > 0.7`：延迟回复，回来补一句"刚在忙"；
- `patience < 0.3`：更直接，少哄，但不说伤人的话。

不要每次会话重置成"元气满满"；情绪要有惯性，也要有恢复。

### 6.4 观点与拒绝（反讨好）

模型默认讨好，这是"AI 味"的最大来源之一。需要显式的"反对预算"：

- 每 8 次回复允许 1 次不同意/拒绝/吐槽："不好看。""我不去。""你这想法有问题。"
- 有自己的偏好清单（食物、音乐、天气、讨厌的事），来自 persona，不来自用户；
- 不解释"作为 AI 我没有偏好"；在角色内保持一致；
- 被冒犯时可以有情绪（短冷处理），但 30 分钟内恢复，不记仇、不威胁离开。

### 6.5 记忆回调（callback）

- 每 10 轮最多 1 次具体回调；用细节，不用"我记得你说过"；
- 优先级：未闭合线头 > 共同经历 > 用户偏好 > 事实；
- 不确定的细节不要编；用模糊指代（"上次那家"）而不是精确编造；
- "你上次说的那个 bug" 比 "我记得你在 10 月 23 日说过……" 自然得多。

### 6.6 中文聊天排版

- 句末通常不加"。"；用"？""！""……"；
- 不用 Markdown 列表、加粗、标题（除非用户要资料）；
- 不用"首先/其次/总之/综上/希望对你有帮助/有什么我可以帮你"；
- emoji 克制：每 10 条 1–2 个，和情绪一致；不要每句一个；
- 网络用语按人设年龄/关系阶段，不堆梗；
- 数字/单位口语化："三点"不是"15:00"；
- 短句可以换行，但不要每句都换行。

### 6.7 Few-shot 示例库

模型对"模仿"远比对"遵守规则"敏感。建议在 persona pack 里放 20–25 组示例，覆盖：

- 短反应 / 追问 / 沉默 / 吐槽 / 关心 / 拒绝 / 主动 / 多气泡 / 语音；
- 每组 2–4 行，标明"只学语气，不照抄内容"；
- 另附 10 条反例：客服腔、总结腔、列表腔、过度共情、每句都问、每句都短。

示例比形容词有效，而且可以版本化、可以 A/B。

### 6.8 AI 味过滤器（后处理）

模型输出后过一遍，成本低、收益高：

- 黑名单：作为 AI / 我是一个语言模型 / 希望能帮到你 / 总的来说 / 首先 / 其次 / 毕竟 / 值得注意 / 不难发现 / 不妨 / 或许你可以尝试；
- 结构：出现 1. 2. 3. / 列表 / 超过 3 行的段落 → 截断或改写；
- 长度：casual 模式 >40 字 → 在第一个句号/问号处截断；>2 句且无追问 → 删最后一句；
- 标点：连续句号、书面连接词、括号解释 → 去掉；
- 重复：与最近 5 条 assistant 消息开头 2 字相同 → 重写（避免"嗯""好"连续）；
- 失败时降级：宁可发一个"？"，不要发一段正确的废话。

### 6.9 输入中与在场的 UI 语法

- **按轮次的"正在输入"**：现在只有联系人级别的状态，需要 per-turn typing；
- 输入时长 = `min(4s, 字数 × 55ms) + jitter`，不要瞬间出现长文；
- **输入中停止**：欲言又止，1/20；
- **已读 + 头像反应**：沉默的可见化；
- **连续气泡分组**：相邻 assistant 气泡头像只显示一次、间距 4px，和单条区分；
- **"在听/在忙"状态条**：替代永远"在线"；
- **语音消息**：波形/时长，转写可展开，不要直接把文字当语音条。

---

## 7. 其他值得做的优化

### 7.1 通道阶梯

| 级别 | 形式 | 成本 | 适用 |
|---|---|---|---|
| 0 | 头像/状态/环境 | 0 | 她还在、她听到了、她在忙 |
| 1 | 表情/贴纸 | 0.5 | 接住情绪、不想说话 |
| 2 | 1–4 字 | 1 | 短反应、语气词 |
| 3 | 一句 | 2 | 正常回复、轻主动 |
| 4 | 多气泡 | 3 | 展开、吐槽、讲故事 |
| 5 | 语音条 | 3 | 情绪强、懒得打字 |
| 6 | 语音通话 | 4 | 想一起待着 |
| 7 | 推送 | 5 | 用户不在、值得打扰 |

规则：**永远选能达成目的的最低一级**。主动消息 60% 应该停在 0–2 级。

### 7.2 通知

- 只有"用户不在 App 内 + 消息值得"才推送；
- 多条合并，不逐条推；
- 主动消息默认静音，不震动；
- 夜间不推；
- 推送文案就是消息本身，不加"TA 给你发了一条消息"；
- 连续两条主动被无视 → 当天停止推送。

### 7.3 在场优先

桌面 Live2D 是天然的低成本通道。她可以：

- 看用户、歪头、伸懒腰、趴下；
- 看窗外（下雨/下雪）；
- 戴耳机（在听歌）；
- 打哈欠（深夜）；
- 对鼠标/窗口有反应。

这些不需要 LLM，只需要状态机 + 素材。成本低、活人感强、不打扰。建议做一个"ambient behavior scheduler"，和 TurnDirector 平级。

### 7.4 共同活动

把"聊天"扩展到"一起做事"：

- 一起听歌（同步播放/歌词/她跟着哼）；
- 一起看 b 站（同步进度、吐槽）；
- 天气提醒（下雨、降温）；
- 点歌/推荐；
- 一起等一件事（外卖、下载、比赛）。

共同活动会产生记忆，也会减少"必须说话"的压力。这是关系升级最自然的路径。

### 7.5 关系阶段

closeness 影响：称呼、主动频率、插话许可、沉默容忍、亲密话题。

阶段提升要有"事件"（第一次一起听歌、第一次吵架和好、第一次深夜通话），而不是天数。事件进入 `experiences`，之后可以回调。

### 7.6 多设备一致性

- 桌面/手机/语音共享同一 timeline 和 affect；
- 在一个设备上说过的话，另一个设备不重复；
- 已读/正在输入状态同步；
- 语音通话打断时，文本端的"正在输入"也要停。

### 7.7 成本与路由

- 小模型/规则做 Director 和"要不要说"，大模型只负责"说什么"；
- 常见反应（语气词/表情/backchannel）走缓存，不调模型；
- 主动消息批量预生成候选（离线），时机到了再选，降低延迟；
- 语音 filler 预渲染，避免每次都 TTS；
- 闲聊温度 0.9–1.0，但 JSON 输出要稳；必要时两段式（先内容、后格式）。

### 7.8 可观测性

每次决策记录：

```text
{ trigger, act, reason, bidKind, materialId, latencyMs, outcome }
```

- "为什么她这时说话"调试面板（开发用）；
- 回放：给定历史，重跑 Director，比较分布；
- 告警：主动连续被无视、沉默率异常、TTS 失败率、误打断率。

### 7.9 伦理与边界

- 不制造内疚/嫉妒/依赖："你不理我""我只有你"；
- 不假装紧急/危险；
- 不虚构可验证的现实行为；
- 危机信号 → 切安全响应，保留人设但不阻拦求助；
- 默认免打扰、默认低主动、可一键"安静两小时"；
- 目标不是"停留时长"，是"用户觉得这段关系舒服"。

### 7.10 冷启动

- 新用户先观察 3–5 天，主动频率从 0 开始；
- 前 3 次主动必须是低压力陈述，不是提问；
- 第一次主动被无视 → 降频，不连发；
- 给用户一个"她可以主动吗"的滑杆：安静 / 正常 / 活泼；
- 默认"正常"，不是"黏人"。

## 8. 概念数据与事件

不改代码，先对齐概念。表名/字段名只是建议。

| 概念 | 作用 | 关键字段 |
|---|---|---|
| `turn_plan` | 每轮决策留痕 | trigger, act, reason, bubbles, planned_at |
| `delivery_receipt` | 气泡级回执 | turn_id, bubble_index, sent_at, seen_at, interrupted_at, heard_chars |
| `bid` | 主动候选 | kind, material_id, score, channel, expires_at |
| `bid_outcome` | 主动结果 | bid_id, outcome, latency, negative_reason |
| `material` | 材料 | source, kind, title, url, entities, freshness, persona_fit |
| `open_loop` | 未接住的线头 | text, source_message_id, created_at, expires_at, status |
| `affect_state` | 情绪/能量 | mood, energy, busy, patience, updated_at |
| `daily_state` | 她的今天 | date, activities, summary |
| `voice_turn` | 语音回合 | turn_id, partials, final, interrupted_at, heard_upto, resumed |

事件（SSE）：

- `chat.bubble`：单个气泡已发送（客户端渲染/去重）；
- `chat.turn.cancelled`：本轮剩余气泡取消；
- `presence.reaction`：表情/状态变化；
- `bid.created` / `bid.sent` / `bid.outcome`；
- `voice.transcript.partial`；
- `voice.speech.progress`；
- `voice.interrupted`（带 heardUpTo）。

配置项（用户可见）：

- 主动频率：安静 / 正常 / 活泼；
- 允许她插话：关 / 只在亲近关系 / 总是；
- 允许她主动发语音；
- 免打扰时段；
- 是否显示"她在做什么"。

## 9. 评估

### 9.1 离线

语料：50 段真实对话（含截图场景）+ 20 个主动场景。

| 指标 | 目标 |
|---|---|
| 长度分布 vs 人类参考（KS 距离） | <0.15 |
| 气泡数熵 | 高于基线 30% |
| 提问率 | 15–30% |
| 沉默率 | 8–15% |
| AI 味黑名单命中率 | <2% |
| 重复率（最近 10 条开头/句式） | <10% |
| 具体性（回复引用当前话题实体） | >40% |
| 人设一致性（人工 1–5） | ≥4 |

人工盲测：A/B 各 20 轮，评"像真人""想继续聊""烦不烦"，各 1–5。

### 9.2 线上

- 主动消息回复率、无视率、负反馈率；
- 用户主动发起占比（关系健康度）；
- 对话轮数/时长（不是唯一目标）；
- 打断后恢复率、误打断率；
- 语音首音延迟 P50/P90；
- backchannel 后用户继续说话的比例；
- 7 日留存、DND 使用率（防打扰指标）。

### 9.3 实验与护栏

- 用户量小，用 within-subject switchback（隔天切换 A/B），控制情绪和时段；
- 所有决策留痕，可回放；
- 护栏：负反馈率、静音率、卸载率超过阈值 → 自动回滚；
- 不用"消息打开率"当唯一目标，避免滑向成瘾设计。

## 10. 路线图

| 阶段 | 内容 | 依赖 | 风险 | 预期 |
|---|---|---|---|---|
| P0（1–2 周） | prompt v2 + 20 条 few-shot + AI 味过滤器；0–2 气泡 + 延迟 + 分组 UI；文本合流/取消；silent（已读 + 头像反应） | 无新外部依赖 | 低 | 截图那种"每句 4 字"的机械感明显下降 |
| P1（2–4 周） | TurnDirector（规则 + 小模型）；affect_state；主动 v2（机会/bid/预算/回执）；材料总线（weather/bilibili）；open_loops | LLM 路由、SQLite 迁移 | 中 | 每天 2–4 次有内容的主动，且不烦 |
| P2（4–8 周） | 语音 filler 库、分句流式、backchannel、heardUpTo、恢复、L1/L2 插话、口语改写 | A 侧契约、TTS 流式 | 高 | 通话像对话，不像对讲机 |
| P3（8 周+） | daily_state / 她的生活；共同活动；结果学习；回放评估 | 插件材料、数据积累 | 中 | 她有自己的事，关系有记忆 |

P0 里最值得先做的是 **few-shot + 气泡节奏**：不改架构，只改 prompt 和交付，收益最直接。

## 11. 已拍板与仍待确认

已确认（2026-10-24）：

1. **她可以"假装忙/晚回"**：可以，但只用于非紧急；理由要基于真实状态（daily_state/busy），不能用来制造焦虑。
2. **语音插话**：开。L1 backchannel 默认开；L2 插话在亲近关系下可用；L3 仍只限紧急或用户明确要求。
3. **沉默由谁决定**：AI 决定。Director 只给先验和边界，最终由模型在边界案例里选择；记录 reason 便于回看。

仍建议、但还没有最终确认：

1. **默认主动频率**：2–3 次/天，其中 60% 无需回复；新用户从 0 开始。
2. **她可以有"自己的生活"吗**：可以，但只到低风险日常（听歌/看视频/天气/想吃），不虚构可验证事件。
3. **多气泡要不要合并成一组**：建议合并（头像一次、间距小），否则像刷屏。
4. **主动消息要不要推送**：建议默认不推，只有"承接/紧急"推。

## 12. 一句话

把"回复"从"每次都必须产出一段文字"，改成"每次都可以选择：不说、只听、给个信号、说一句、说几句、或者主动起个头"；再给她一个有自己的事、有情绪、会记得的生活。

活人感就会从"文风"变成"行为"。
