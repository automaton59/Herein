# Phase 2 设计：人格、关系、记忆与角色资产

日期：2026-06-19
状态：核心已实现，保留为 Phase 2 设计基准

## 1. 产品方向

此间（Herein）是一个本地优先的私人 IM 陪伴应用。Phase 2 的目标是强化“用户正在和同一个稳定的人长期相处”的感觉。

Phase 2 不是 SillyTavern 克隆，也不以世界书、设定集、分支剧情存档或完整角色卡兼容为目标。SillyTavern 可以作为本地持久化、总结、资产组织和上下文装配的实现参考，但此间应保留自己的产品模型。

Phase 2 的核心目标是让人格、关系、记忆和角色资产成为一个系统：

- 角色像联系人，不像剧情预设。
- 每个角色默认只有一条连续关系时间线。
- 记忆体现生活和关系的发展，而不只是静态事实。
- 用户可以查看、编辑、禁用、置顶和手动新增记忆。
- 主聊天保持干净：不显示 thinking block，不显示原始调试日志，不为每次记忆更新弹确认窗。

## 2. 数据底座

Phase 2 应引入 SQLite 作为长期主数据源。

已确认决策：

- SQLite-first。
- Electron-first。
- 使用 `better-sqlite3`。
- SQLite 只在 Electron main process 中打开。
- Renderer 通过类型明确的 IPC API 访问数据，不能直接打开数据库文件。
- 浏览器模式不再是完整产品目标。如果 SQLite-backed 功能无法在浏览器模式运行，应用应提示开发者或用户使用 Electron。
- `config.json`、`chat-history.json`、`api-profiles.json` 成为 Phase 1 迁移输入，而不是长期存储。
- API key 继续通过 Electron `safeStorage` 加密；加密后的 payload 从 JSON 迁移到 SQLite。
- 大文件保存在文件系统，SQLite 保存引用和 metadata。

SQLite 应启用和支持：

- `WAL` mode。
- `foreign_keys = ON`。
- migration table。
- 多表写入事务。
- 启动完整性检查。
- 不留下半完成状态的备份和恢复流程。

## 3. 主时间线模型

Phase 1 支持一个角色多个会话。Phase 2 应收敛到更接近陪伴应用的模型：

- 一个角色默认只有一条主聊天时间线。
- 角色是联系人，时间线是关系本身。
- 主界面应呈现为联系人列表，而不是“角色下拉选择器 + 聊天记录列表”。
- 角色名是默认聊天显示名；用户可设置本地备注，显示为 `备注 || 角色名`。
- 备注只用于本地 UI 展示，不进入 prompt，不改变角色本体身份。若要让角色知道某个称呼，应写入角色设定、关系档案或记忆。
- 长历史通过分页、搜索、时间分段、总结和记忆管理，而不是通过打开多个互相独立的聊天来切断。
- Phase 1 既有多会话数据需要谨慎迁移。最新或当前会话可以成为主时间线，旧会话进入历史归档。
- 历史归档应可查看，也可以在未来被显式用于记忆提取，但不应默认静默参与当前上下文。

如果用户想重新开始，应用应提供明确动作：

- 重置关系。
- 清空记忆。
- 复制角色为一个新联系人。

## 4. 角色与关系模型

Phase 2 应把 Phase 1 的简单 `CharacterConfig` 升级为联系人式角色档案。

角色档案应包括：

- 显示名、昵称、头像、简介、第一条消息。
- 人格核心：说话方式、价值观、边界、情绪表达习惯。
- 角色资料字段只描述角色本体；行为约束 prompt 由产品内部维护，不作为用户可编辑字段。
- 资产引用：头像、未来表情、Live2D、视频聊天素材。

联系人式 UI 的职责分层：

- 左侧联系人列表只负责进入角色的一条主聊天。
- 聊天顶栏显示头像、联系人显示名和状态；点击头像或名称进入联系人资料。
- 联系人资料抽屉承载本地备注、头像上传、角色卡设置入口和清空聊天等低频操作。
- 角色卡预览不应常驻主聊天侧栏，以免和角色设置入口重复并抢占聊天视线。

关系档案应与静态角色身份分开：

- 当前关系基调。
- 熟悉程度或亲近程度。
- 共同习惯和私密语言。
- 重要共同经历。
- 当前未收束的话题或情绪上下文。

用户资料应分层：

- 用户基础资料和长期偏好可以跨角色共享。
- 关系记忆、共同经历、角色特定称呼必须按角色隔离。

## 5. 记忆模型

Phase 2 使用双层记忆系统：

1. 会话总结：总结长段对话。
2. 结构化记忆：保存重要、稳定或值得长期引用的信息与事件。

会话总结是长聊天的主要压力阀。它负责概括最近聊了什么、情绪走向、当前话题状态、尚未收尾的事情，以及下次回复需要延续的上下文。

结构化记忆是锚点。它应该少而准，例如：

- 某天晚上用户送过礼物。
- 用户不喜欢某个称呼。
- 用户下周要从杭州搬去上海。
- 角色和用户约定睡前说晚安。

记忆不是静态事实表，而是会随生活和关系自然发展的档案：

- 状态型记忆有当前值和历史脉络。
- 事件型记忆进入时间线，不被覆盖。
- 偏好型记忆可以随时间改变。
- 关系型记忆属于某个角色关系。

示例：

- 当前：用户最近在杭州，并提到下周要搬去上海。
- 之后：用户现在在上海；之前在杭州。

这不是冲突，而是自然发展。

记忆条目应追踪：

- 类型：`state`、`event`、`preference`、`relationship`、`profile`。
- 作用域：`global`、`character`、`timeline`。
- 当前内容。
- 有用时记录 previous value 或历史说明。
- 来源消息 id 或来源时间。
- 置信度。
- 来源：manual、auto、summary、imported。
- 状态：active、disabled、pinned、hidden from context。

手动记忆是一等能力。用户必须能直接新增一条记忆，而不是等待模型从聊天中推断出来。

## 6. 自动总结与抽取

记忆更新应自动、非打扰。

已确认决策：

- 在助手回复完成后，按消息数、字数或 token 阈值触发总结和抽取。
- 不等到上下文快满才总结。
- 不为每次记忆变化弹确认窗。
- 成功更新直接写入记忆层。
- 失败结果隔离保存，不能覆盖旧的好总结。

记忆模型使用全局设置：

- 默认跟随当前聊天 API profile。
- 用户可选择一个全局记忆/总结专用 API profile。
- Phase 2 不做每角色单独记忆模型 override。
- 记忆调用应使用产品内部独立 prompt、低温度、结构化 JSON 输出、校验和独立错误状态。
- 总结和结构化抽取 prompt 不作为用户设置项暴露，避免用户或后续实现把核心行为变成脆弱的配置拼接。
- 如果指定的记忆 profile 缺失或不可用，则回退当前聊天 profile，并在记忆/设置界面显示原因。

模型输出必须结构化并校验后再入库。如果解析失败，或者模型把总结任务写成了下一段对话回复，应用应保留上一版总结，并记录这次失败供查看。

## 7. 上下文装配

当前直接拼角色 system prompt 的流程应升级为上下文装配服务。

上下文应按确定顺序装配：

- 角色身份和稳定人格。
- 关系档案。
- 当前用户资料。
- 当前状态型记忆。
- 相关偏好。
- 关系记忆。
- 重要共同事件。
- 当前时间线总结。
- 最近消息。

主聊天仍保持干净，但用户应能查看角色下一次回复会参考什么。产品侧命名可以是“下次回复会参考”，比纯粹的“debug context”更合适。

上下文查看应可折叠、可读，解释本次选中的总结和记忆，不暴露原始数据库细节。

## 8. 记忆 UI 与设置

Phase 2 应有两层 UI。

聊天侧记忆面板：

- 从当前聊天/联系人进入。
- 显示当前时间线总结。
- 显示当前角色关系的关键记忆。
- 显示关系状态和共同经历。
- 显示最近自动记忆更新。
- 显示下次回复会参考的内容。
- 支持编辑、删除、禁用、置顶和手动新增记忆。

设置里的记忆页：

- 记忆功能开关。
- 总结触发阈值。
- 全局记忆/总结 API profile。
- 输出校验和失败处理。
- 备份/恢复入口，或链接到数据页。

聊天侧面板是正式产品界面，不只是开发调试工具。

## 9. 角色档案、资产、导入与导出

Phase 2 应支持此间内部角色导入导出。

这不是 SillyTavern 兼容。此间可以借鉴已有格式，但 Phase 2 应优先服务自己的联系人、人格、关系模型。

建议提供两种导出：

- 角色档案：适合分享或迁移角色本体。包含角色资料、人格、问候和资产引用。默认不包含私人关系记忆、聊天历史或内部产品 prompt。
- 完整角色归档：适合用户自己的私密备份或迁移。包含角色档案、资产、关系状态、记忆、总结和主时间线。

资产应存放在使用稳定 character id 或 asset id 的目录中，UI 展示友好角色名。角色改名不能导致资产引用断掉。

头像上传应按资产处理：

- 用户从本地选择图片。
- Electron main process 复制图片到 `data/assets/<characterId>/`。
- SQLite `assets` 表保存 `asset id`、相对路径、类型和 MIME。
- 角色档案只保存 `avatarAssetId` 引用。
- Renderer 可通过只读 API 获取头像渲染用 data URL，但 base64 不作为长期存储格式。

## 10. 备份、迁移与恢复

Phase 2 应提供完整本地数据安全能力。

备份：

- 导出 zip 包。
- 包含 `manifest.json`、`app.db`、`assets/`。
- 默认不导出 API key。
- 如果用户明确选择包含 API 凭据，需要提示 `safeStorage` 密文可能无法跨机器或跨系统用户解密。

恢复：

- 校验 manifest 和 schema version。
- 如有 checksum，校验文件完整性。
- 替换前先创建当前数据快照。
- 数据库和 assets 一起恢复。
- 恢复失败时回滚。

迁移：

- 首次 Phase 2 启动时，将 Phase 1 JSON 文件迁移进 SQLite。
- 保留 Phase 1 JSON 文件作为备份，不自动删除。
- 记录迁移状态和版本。
- 迁移应可重试，避免失败后重复插入数据。

## 11. 非目标

Phase 2 不做：

- 世界书、设定集、剧情书系统。
- 把 SillyTavern 兼容作为产品目标。
- 把分支剧情存档作为主聊天模型。
- 每角色记忆模型设置。
- 复杂 prompt manager。
- 插件市场。
- 云账号或云数据库依赖。
- 在聊天正文展示 thinking/reasoning。

## 12. 实现落点

自然代码落点：

- 将 `src/stores/chat.ts` 里直接使用 `buildCharacterSystemPrompt(character)` 的位置替换为上下文装配。
- 将长期应用数据访问迁移到 Electron main process 的 SQLite IPC 服务。
- 用 SQLite-backed repository 逐步替代 `src/services/storage/index.ts` 作为应用数据主存储。
- 保留 Electron 的 `safeStorage` 加解密能力。
- 添加 Phase 1 JSON 迁移。
- 在设置和聊天侧添加记忆、角色档案和备份相关 UI。

## 13. 验证要求

Phase 2 未通过以下验证前不应视为完成：

- 空数据启动 Electron 能创建有效 SQLite 数据库。
- 既有 Phase 1 JSON 数据能迁移进 SQLite。
- API profiles 和加密 key 在迁移后重启仍可用。
- 一个角色映射到一条主时间线。
- 自动总结按阈值触发。
- 坏总结输出不会覆盖上一版好总结。
- 手动记忆可以新增并进入上下文。
- 禁用记忆不会进入上下文。
- 备份 zip 能导出数据库和 assets。
- 恢复可以从备份恢复，并能在失败时回滚。
- 纯浏览器模式要么明确提示不支持完整存储，要么保持有意限制。
