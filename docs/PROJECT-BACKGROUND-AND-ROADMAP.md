# 此间 / Herein 项目背景与路线图

最后更新：2026-06-20

## 1. 项目定位

此间（Herein）是一个本地优先的私人陪伴应用。

它的核心体验不是“配置一个 AI 工具”，也不是“在多个角色之间挑选”。角色由私有 persona 包固定；应用启动后，用户应该先看到桌面上的 Live2D 形象，再打开一段熟悉的私聊：稳定人格、在线状态、正在输入、聊天气泡、历史会话，以及一个逐渐稳定下来的关系对象。

此间不以 SillyTavern 式剧情玩法为目标，也不追求把世界书、设定集、复杂剧情结构搬进来。SillyTavern 可以作为本地持久化、总结、资产和上下文装配的实现参考，但不是此间的产品目标。

## 2. 产品原则

### 2.1 像真人 IM

默认体验应接近 QQ、微信或其他私人聊天工具：

- 头像旁显示在线状态。
- 用户发送后显示“正在输入...”。
- 回复完成后整条出现，不默认做逐字流式输出。
- 用户可以撤回仍在发送中的消息，并打断请求。
- 错误状态要清楚，但不要把底层 API 调试感暴露给普通聊天。

### 2.2 不展示思维过程

此间里的聊天对象不应把 thinking block 或 reasoning 作为聊天内容展示。底层可以解析 reasoning，用于兼容部分模型响应格式或未来诊断，但普通用户体验中不显示、不强调，也不把它作为角色说出的话保存。

### 2.3 情绪是元数据，不是正文

模型可以输出类似 `[happy]` 或 `[emotion: happy]` 的标签，但前端应从正文中剥离。情绪只作为 metadata 保存，用于后续头像、表情、Live2D、视频聊天或状态变化。

### 2.4 本地优先

用户的角色、聊天、记忆、关系资料、API profile 默认保存在本机。应用可以调用用户配置的第三方 LLM API，但不应把此间自己设计成强依赖云端账号和云端数据库的产品。

### 2.5 API 中立

此间应尽量兼容 OpenAI-compatible API。用户可以使用 OpenAI、DeepSeek、OpenRouter、AnyRouter、OpenCode 或其他兼容端点。具体 provider 的差异应尽量被 profile 和 adapter 消化，而不是散落在 UI 和业务代码里。

### 2.6 形象先于聊天，关闭不是退出

桌面形象是应用的一等入口，不藏在聊天或视频通话后面。关闭主窗口只收起聊天，形象和本地服务继续在线；用户显式退出才结束进程。这个行为由托盘和后台托管生命周期保证。

### 2.7 质量每阶段都做

测试、构建、迁移、安全、文档不是最后一个 Phase 才做的“收尾”。每一个阶段结束时都应该跑一轮完整检查，避免功能越堆越难维护。

## 3. 当前 Phase 1：私人 IM MVP

Phase 1 已完成，目标是把项目从基础 Demo 推到可日常试用的桌面聊天应用。

已完成能力：

- Electron + Vite 开发启动流程。
- API profile 管理：新建、保存、切换、删除、测试连接、获取模型。
- API key 与 profile 配对保存。
- Electron 下使用 `safeStorage` 加密 API key。
- 本地 JSON 文件存储：配置、聊天历史、API profiles。
- 浏览器开发模式 localStorage fallback。
- 多角色、多会话。
- 会话绑定角色。
- 消息编辑、撤回打断、重新生成、删除后续。
- 默认完整回复，不做逐字流式展示。
- 主聊天隐藏 thinking/reasoning。
- 情绪标签从正文剥离，仅保留 metadata。
- IM 风格 UI。
- 独立设置页。
- Light / Dark / System 主题。
- 自定义下拉菜单，避免原生 select 在暗色模式下割裂。

Phase 1 的意义是打通基础链路：用户能配置 API，能稳定聊天，数据能在本机保存，聊天体验已经从“模型调试窗口”转向“私人聊天空间”。

## 4. Phase 2：人格、关系、记忆与角色资产

Phase 2 已基本收尾，核心能力已经落地。后续 Phase 2 只保留发布前性质的收口工作：真实 Electron smoke、打包验证、关系档案 UI 增强、记忆合并/搜索策略，以及为 Phase 3 的角色存在感继续补资产管理。

它合并了原本可能拆开的“角色管理”和“记忆系统”。角色资料、人设稳定、长期记忆、关系档案、上下文装配，本质上都在解决同一个问题：让聊天对象在长期聊天中像同一个人，而不是每次对话都重新生成一个临时人格。

完整设计见：

- `docs/superpowers/specs/2026-06-19-phase2-personality-relationship-memory-assets-design.md`

### 4.1 SQLite-first 数据底座

Phase 2 不再继续把 JSON 作为长期主存储，也不再把浏览器 fallback 作为完整产品约束。

已确认方向：

- Electron-first。
- SQLite-first。
- 使用 `better-sqlite3`。
- SQLite 只在 Electron main process 打开。
- React renderer 通过受控 IPC 调用数据服务。
- 启用 `WAL`、`foreign_keys`、migration table 和事务。
- `config.json`、`chat-history.json`、`api-profiles.json` 是 Phase 1 迁移输入，不是 Phase 2 长期主存储。
- API key 仍使用 Electron `safeStorage` 加密，密文进入 SQLite。
- 浏览器模式可以保留有限前端调试能力，但 SQLite-backed 功能不要求在纯浏览器完整运行。

### 4.2 固定角色单主时间线

Phase 3E 之后，应用只服务 persona 包指定的一个角色，不再提供角色选择或新建/复制/删除入口。角色仍然像一个长期联系人，而不是剧情卡存档。

该角色只有一条连续主聊天时间线：

- 长聊天通过分页、搜索、时间分段、总结和记忆承接。
- 不再把“同一角色开多个聊天”作为常规入口。
- 如果用户要重新开始，应提供明确动作：重置关系、清空记忆、复制角色为新角色。
- Phase 1 既有多会话迁移为历史归档；最新或当前会话成为主时间线，旧会话默认不参与当前上下文。

### 4.3 人格与关系档案

角色资料不应该变成设定集堆叠。它更像联系人档案和人格档案：

- 基本资料：姓名、头像、称呼、简介、默认问候。
- 人格核心：说话方式、价值观、边界、情绪表达习惯。
- Prompt 字段：哪些长期固定，哪些按上下文动态装配。
- 资源索引：头像、未来表情、Live2D、视频聊天素材。

关系档案应与静态角色身份分开：

- 当前关系基调。
- 熟悉程度或亲近程度。
- 共同习惯、私密称呼、互动方式。
- 重要共同经历。
- 当前未收束的话题或情绪状态。

用户基础资料和长期偏好可以跨角色共享；关系记忆、共同经历、角色称呼必须按角色隔离。

### 4.4 双层记忆系统

Phase 2 使用两层记忆：

- 会话总结：承接大篇幅长对话，是主要压力阀。
- 结构化记忆：记录重要信息、偏好、状态变化、关系事件和共同经历。

记忆不是静态事实库，而是会随生活和关系自然发展的档案：

- 状态型记忆有当前值和历史脉络。
- 事件型记忆进入时间线，不被覆盖。
- 偏好型记忆可以随时间修订。
- 关系型记忆按角色隔离。

例如用户以前说“我最近在杭州”，后来又说“我下周搬去上海了”，这不是冲突，而是自然发展。合理记忆是：用户最近在杭州，并提到下周要搬去上海；之后再更新为用户现在在上海，之前在杭州。

用户必须能查看、编辑、删除、禁用、置顶、手动新增记忆。自动记忆入库不应每次弹窗确认，但必须可见、可改、可追溯。

### 4.5 自动总结与记忆抽取

自动总结和结构化记忆抽取应按消息数、字数或 token 阈值主动触发，而不是等上下文快满再补救。

已确认方向：

- 助手回复完成后检查是否达到阈值。
- 达到阈值后后台更新会话总结并抽取少量结构化记忆。
- 不阻塞聊天，不弹确认窗。
- 更新失败不覆盖上一版好总结。
- 抽取结果使用结构化 JSON，并进行校验。
- 记忆/总结模型是全局设置：默认跟随当前聊天 API profile，也可以选择一个全局记忆专用 profile。
- 不做每角色单独记忆模型设置。

### 4.6 上下文装配

Phase 2 已把直接拼接角色 system prompt 的流程升级为上下文装配器。

装配内容按确定顺序组织：

- 角色身份和稳定人格。
- 关系档案。
- 全局用户资料。
- 当前状态记忆。
- 偏好记忆。
- 关系记忆。
- 重要共同事件。
- 当前时间线总结。
- 最近消息。

聊天侧可以提供“下次回复会参考”这样的正式产品入口，用于查看当前会被带入上下文的摘要和记忆。它不是纯调试面板，也不应暴露数据库细节。

### 4.7 记忆 UI 与设置页

Phase 2 已有两层 UI：

- 聊天侧记忆面板：查看和编辑当前角色/当前关系的总结、记忆、关系状态、最近自动更新、下次回复会参考的内容。
- 设置里的记忆页：配置记忆开关、触发阈值、全局记忆 API profile、输出校验和失败处理策略；总结和抽取 prompt 是内部产品逻辑，不作为用户设置暴露。

### 4.8 角色档案、资产与导入导出

Phase 2 支持此间内部角色档案导入导出。这不是 SillyTavern 兼容目标。

建议区分：

- 角色档案导出：用于分享或迁移角色本体，包含姓名、头像、人格、说话方式、默认问候、资源引用。默认不包含私人关系、聊天记录、记忆或内部产品 prompt。
- 完整角色归档：用于用户自己的私密迁移，包含角色档案、资产、关系状态、记忆、阶段总结、主时间线。

资产目录应使用稳定 id，而不是显示名。用户体验中显示友好角色名；底层引用不能因改名断掉。

### 4.9 全量备份、迁移、恢复

Phase 2 已提供基础数据安全能力：

- 全量备份导出 zip。
- zip 包含 `manifest.json`、`app.db`、`assets/`。
- 默认不包含可解密 API key。
- 如果用户明确选择包含 API 凭据，需提示 `safeStorage` 密文可能无法跨机器或跨系统用户解密。
- 恢复前先创建当前数据快照。
- 恢复时校验 manifest、schema version 和文件完整性。
- 迁移 Phase 1 JSON 前保留旧数据备份，迁移失败可重试。

## 5. Phase 3：角色存在感与桌面陪伴

Phase 3 进入更强的角色存在感。它不是把此间改成游戏引擎，也不是给角色卡系统继续堆字段，而是让固定角色在聊天之外有可感知的状态、表情、形象和声音。

详细交接见：

- `docs/PHASE3-HANDOVER.md`
- `docs/DESKTOP-PRESENCE.md`
- `docs/superpowers/specs/2026-06-20-phase3-video-call-presence-design.md`

阶段目标：

- 把 Phase 1/2 已有的 `emotion` metadata 发展成展示状态管线。
- 让头像、表情图、Live2D 或等价动态形象由同一套资产索引驱动。
- 提供视频聊天式界面，但不替代主聊天；它是当前联系人的另一种进入方式。
- 让关系状态、最近情绪和未收束上下文能影响表情、状态文案和动作反馈。
- 语音输入和 TTS 已以本地系统语音第一版进入 Phase 3D；云端 provider 和角色级声音配置仍应作为独立子任务，不要阻塞表情/形象链路。

Phase 3A–3D 先验证了视频通话式存在感；Phase 3E 已把形象入口从通话窗口前移到应用启动：

1. 应用启动即创建透明、置顶的桌面 Live2D 形象窗口。
2. 聊天页不再提供角色选择；角色由 persona 包固定，聊天、记忆和形象共用同一身份。
3. 关闭主窗口进入后台托管：主窗口隐藏到托盘，形象和内嵌 Core 保持在线；显式退出才结束进程。
4. 形象资产优先使用 persona 的 `avatar.entry`，用户显式导入的新资产可以覆盖；旧视频通话时代的资产不会静默抢占。
5. 视频通话窗口保留为可选的语音/沉浸视图，不再是 Live2D 的唯一入口；后续应把语音接到桌面形象并移除重复渲染。
6. 后续再把 presentation state 深化为可复用管线，让表情、动作、语音和更细状态复用同一套信号。

Phase 2 已经提供 `emotion` metadata、头像资产链路、assets 表、关系档案、记忆和内部 prompt，这些都应成为 Phase 3 的基础。

## 6. Phase 4+：功能池

Phase 4 之后不固定成某一个单一大主题，而是根据产品实际使用情况挑选功能。

候选方向：

- 正式打包和发布：exe、dmg、AppImage。
- 移动端聊天：PWA、Capacitor、React Native 或原生 APK 再评估。
- 工具调用：天气、时间、日程、搜索、本地文件、网页信息。
- 主动聊天：可控、低打扰、有免打扰和频率限制。
- 插件或技能系统。
- 多端同步或云备份，但默认仍本地优先。
- 更细的隐私、安全、成本和 token 使用控制。

## 7. 明确不做或暂不做

这些内容不是当前主线：

- 世界书、设定集、剧情书式玩法。
- 把 SillyTavern 完整兼容作为核心目标。
- 把同一角色多分支聊天作为主流程。
- 每个角色单独配置记忆模型。
- 在主聊天里显示 thinking block。
- 默认逐字流式输出。
- 先做大而全的插件市场或角色社区。
- 强依赖云账号或云数据库。

这些不是永远不能做，而是它们不应挤占此间当前最重要的目标：建立一个更真实、稳定、可长期相处的私人聊天对象。

## 8. 每阶段固定收尾

每个 Phase 结束前都应至少完成：

- `npm run build`
- `npm run electron:compile`
- 核心聊天链路手动回归。
- API profile 新建、切换、删除、重启验证。
- 数据迁移和备份验证。
- 亮色、暗色、窄屏 UI 检查。
- 搜索真实 API key，确认没有进入仓库。
- 更新 README、交接文档和路线图。
